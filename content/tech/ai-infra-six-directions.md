读完芥末的[《AI Infra 六个关键方向：从分布式推理到 Agent 沙箱》](https://www.zhang-jian.com/archives/2026-01-23-ai-infra-six-key-directions)，我更关注其中的系统设计问题：请求怎样分配、数据怎样流动、硬件为什么会闲着，以及模型生成的代码应该在哪里执行。下面按自己的理解做一个简要整理。

## 1. 分布式推理：按不同阶段分配资源

大模型回答问题时，先处理输入的整段上下文，再逐个生成 token。前者是 Prefill，后者是 Decode，两者的计算与访存特征不同。

PD 分离把它们交给不同的资源池，分别优化首 token 延迟和后续生成速度。拆开以后，还要处理 KV cache 传输、负载均衡和扩缩容。MoE 模型还涉及 token 在不同专家之间的路由与通信。[DistServe](https://arxiv.org/abs/2401.09670)和 [DeepEP](https://github.com/deepseek-ai/DeepEP)分别对应其中的阶段拆分与专家通信问题。

## 2. 算子与编译：把单张卡上的计算做好

集群调度解决“交给谁算”，算子优化解决“拿到任务后怎样算得快”。

矩阵乘法和 Attention 等操作，需要安排好数据分块、内存搬运与计算流水线。[TileLang](https://github.com/tile-ai/tilelang)这类工具，让开发者在 tile 层面描述计算，再由编译器承担一部分底层调度工作。它降低了开发成本，性能仍需要结合具体硬件验证。

## 3. RL 训推分离：让生成数据和训练互相接得上

强化学习中，模型先生成回答或执行任务，获得反馈，再用这些经历更新参数。生成轨迹和参数训练是两类工作，可以独立部署与调度。

分离之后，重点是保留完整轨迹、管理模型版本，并减少“训练等数据、生成端等资源”的空转。[SeamlessFlow](https://arxiv.org/abs/2508.11553)就是围绕这类数据流与资源调度展开的方案。

## 4. 模型与系统协同：设计模型时就考虑部署

模型的参数量相近，实际运行成本也可能差很多。Attention 结构、KV cache 大小、专家激活方式和量化精度，都会改变硬件上的瓶颈。

我的理解是，模型结构与部署方案应该一起评估：既看效果，也看算力、显存和网络能否承受。[Step-3](https://arxiv.org/abs/2507.19427)将模型设计与 Attention、FFN 的分离部署结合起来，是一个具体例子。

## 5. Agent Infra：管理一次任务的执行过程

Agent 会调用工具、读写文件、执行代码，一次任务可能持续很多轮。基础设施因此需要管理权限、执行环境、任务状态和日志。

我比较关注两个问题：失败后能否接着执行，以及代码运行会影响到多大的范围。沙箱隔离、状态持久化、超时和资源限额，都要落到具体机制上。[Firecracker](https://firecracker-microvm.github.io/)这类轻量虚拟化技术，提供了构建隔离执行环境的一种基础能力。

## 6. 超节点与高速互联：减少多卡协作的等待

多张 GPU 一起工作时，需要持续交换数据。卡的数量增加以后，通信可能成为限制。

超节点通过高带宽互联扩大紧密协作的 GPU 范围，为模型并行和跨卡数据交换提供基础。以 [NVLink](https://www.nvidia.com/en-us/data-center/nvlink/)为例，互联能力也是系统设计的一项约束，硬件拓扑、任务放置和通信方式需要配合考虑。

对我来说，这六个方向可以作为排查问题的索引：一次请求变慢，先看排队、计算、访存和通信；一个 Agent 任务跑不完，再看状态、工具与执行环境。先找到等待发生在哪里，再决定优化哪一层。
